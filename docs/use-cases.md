# Сценарии использования
Версия: 22.02.2026

**Роли в проекте:**
1. **Администратор** - отвечает за развертывание, техническое состояние и сохранность данных системы. Не участвует в учебном процессе напрямую.  
2. **Преподаватель** - создает формы и таблицы, настраивает доступы.  
3. **Студент** - заполняет формы, просматривает и редактирует таблицы в рамках   предоставленных прав.  

___

## 1. Пользовательские сценарии
### Use Case 1: Сквозной цикл организации учебного процесса
*Эти сценарии описывают жизненный цикл учебного процесса. Преподаватели и студенты взаимодействуют с интерфейсом таблиц как конечные пользователи.*  

**Действующее лицо:** Преподаватель.    
**Предусловие:** Преподаватель и студенты авторизованы в системе.  
**Основной сценарий:**  
1. Преподаватель создает новую таблицу и форму для сбора данных от студентов.
2. В интерфейсе таблиц преподаватель настраивает автоматическое получение ответов из формы в таблицу
3. Преподаватель открывает доступ студентам к форме (на заполнение) и к итоговой таблице (на чтение).
4. При заполнении формы студентами данные автоматически отображаются в таблице.
5. Преподаватель и студенты одновременно редактируют таблицу (например, при выполнении группового задания, в случае, если выданы права на редактирование)
6. По завершению совместной работы над таблицей преподаватель переводит таблицу в режим "Только чтение" и публикует ссылку на соответствующую таблицу.
7. Система архивирует данные, обеспечивая сохранность результатов.

**Альтернативный сценарий:** Если ответ от студента уже зафиксирован в системе, приложение обновляет существующую запись или выводит предупреждение о дубликате.  

**Результат:** Настроена автоматическая цепочка сбора и агрегации данных. Получен организованный процесс сбора данных  

### Use Case 2: Автоматизированный учет активности (Commitment)
**Действующее лицо:** Преподаватель.  
**Предусловие:** В таблице заполнены ссылки на GitHub-репозитории студентов.  
**Основной сценарий:**  
1. Преподаватель инициирует функцию сбора статистики из репозиториев.
2. Приложение обращается к API GitHub, анализирует количество коммитов и активность студентов.
3. Приложение рассчитывает итоговый показатель участия на основе заданных алгоритмов.
4. Приложение автоматически обновляет данные в исходной таблице.

**Результат:** Получены актуальные данные об активности студентов без ручного анализа репозиториев.

### Use Case 3: Взаимодействие студента с системой
**Действующее лицо:** Студент.  
**Основной сценарий:**  
1. Студент переходит по ссылке на форму, предоставленную преподавателем, заполняет необходимые поля и отправляет ответ.
2. Студент переходит по ссылке на таблицу для просмотра результатов.
3. Студент просматривает информацию и/или вносит правки, если предоставлены права на редактирование.

**Альтернативный сценарий (Нет доступа):**
1. Студент пытается открыть таблицу по ссылке, на которую у него нет прав.
2. Система определяет отсутствие прав и выводит сообщение об отказе в доступе.

**Результат:** Данные студента зафиксированы в системе; обеспечена возможность работы с таблицами согласно установленным правам доступа.

## 2. Эксплуатационные сценарии
*Эти сценарии описывают работу администратора и скриптов, которые обеспечивают жизнедеятельность системы.*  

### Use Case 1: Автоматизированный деплой системы
**Действующее лицо:** Администратор.  
**Предусловие:** На сервере установлены все зависимости, подготовлены файлы конфигурации.  
**Основной сценарий:**  
1. Администратор запускает скрипт деплоя.
2. Скрипт проверяет настройки Docker, а также наличие свободных портов.
3. Приложение разворачивает контейнеры (БД, сервис таблиц, сервис форм) и выполняет автоматическую настройку интеграции между сервисами.
4. Приложение выводит сообщение об успешном запуске и URL-адреса развернутых сервисов.

**Альтернативный сценарий:**
1. Скрипт обнаруживает конфликт портов или нехватку прав.
2. Процесс прерывается, приложение выводит сообщение с указанием ошибки.

**Результат:** Система развернута и готова к работе.

### Use Case 2: Проверка статуса системы (Health-check)
**Действующее лицо:** Администратор.  
**Предусловие:** Система была предварительно развернута.  
**Основной сценарий:**  
1. Администратор запускает скрипт проверки статуса.
2. Приложение опрашивает каждый контейнер на предмет активности (статус Running).
3. Приложение проверяет наличие соединения с базой данных и отклик API (код 200).
4. Приложение выводит краткий отчет о доступности всех компонентов.

**Результат:** Получена актуальная информация о состоянии всех элементов системы.

### Use Case 3: Мониторинг ресурсов и аналитика нагрузки
**Действующее лицо:** Администратор.  
**Основной сценарий:**  
1. Администратор запускает скрипт сбора метрик.
2. Приложение собирает данные: CPU, RAM, количество активных сессий, среднее время отклика API.
3. Приложение формирует отчет (в формате JSON или HTML) с данными по нагрузке.

**Результат:** Получена актуальная информация о нагрузке системы.

### Use Case 4: Резервное копирование и восстановление
**Действующее лицо:** Администратор.  
**Предусловие:** Система запущена, содержит пользовательские данные.  
**Основной сценарий (Создание бэкапа):**
1. Администратор запускает скрипт создания бэкапа.
2. Приложение создает дамп базы данных и архивирует файлы конфигурации.
3. Архив (артефакт .tar.gz / .zip) сохраняется в локальное хранилище.

**Альтернативный сценарий (Ошибка создания бэкапа):**
1. На диске недостаточно места для создания архива, или возникла другая техническая причина, по которой бэкап не может быть создан.
2. Скрипт прерывает работу и возвращает сообщение о соответствующей ошибке.

**Результат:** Успешно создана резервная копия данных.  

**Сценарий восстановления:**
1. Администратор запускает скрипт восстановления, указывая бэкап.
2. Система восстанавливает структуру БД и данные, после чего перезапускает сервисы.

**Результат:** Данные успешно восстановлены из копии.
