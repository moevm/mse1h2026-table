# Сценарии использования
Версия: 19.02.2026 - 21.02.2026

Роли на текущий момент:
1. Администратор
2. Преподаватель
3. Студент

___

## 1. Администратор

### Use Case 1: Автоматизированный деплой системы
**Действующее лицо:** Администратор
**Предусловие:** На сервере установлены все зависимости (Python, Docker и т.д.), нет ошибок в реализации ПО проекта, подготовлены файлы конфигурации
**Основной сценарий:**
1. Администратор запускает скрипт деплоя
2. Скрипт проверяет настройки Docker, наличие свободных портов
3. Приложение разворачивает контейнеры и выполняет автоматическую настройку интеграции между сервисами
4. Приложение выводит сообщение об успешном запуске

**Альтернативный сценарий:**
1. Во время деплоя возникает конфликт портов или ошибка сети
2. Приложение выводит сообщение об ошибке

**Результат:** Система развернута и готова к работе

### Use Case 2: Мониторинг ресурсов и статуса
**Действующее лицо:** Администратор
**Предусловие:** Сервисы запущены
**Основной сценарий:**
1. Администратор запускает скрипт проверки статуса
2. Приложение собирает метрики, количество активных таблиц, расход ресурсов на одного пользователя.
3. Приложение выводит отчет 
**Результат:** Администратор получает актуальную информацию о нагрузке и работоспособности системы

### Use Case 3: Бэкапы. Резервное копирование и восстановление
**Действующее лицо:** Администратор
**Предусловие:** Система запущена, содержит пользовательские данные
**Основной сценарий:**
1. Администратор запускает скрипт создания бэкапа
2. Приложение сохраняет бэкап
3. (Для восстановления) Администратор запускает скрипт восстановления
4. Приложение заменяет данные на данные бэкапа и перезапускает контейнеры
**Результат:** Создана копия данных или система возвращена к предыдущему состоянию.

## 2. Преподаватель

### Use Case 1: Импортирование пользователей (Массовое создание пользователей)
**Действующее лицо:** Преподаватель 
**Предусловие:** Имеется файл со списком студентов
**Основной сценарий:**
1. Преподаватель запускает скрипт импорта пользователей из файлы
2. Приложение считывает данные и создает учетные записи в системе таблиц
3. Приложение назначает базовые права доступа для пользователей
**Альтернативный сценарий:** Если пользователь уже существует, скрипт обновляет его данные или выдает предупреждение
**Результат:** Созданы аккаунты для всей группы студентов

### Use Case 2: Импорт таблиц (import range. уточнить)
**Действующее лицо:** Преподаватель 
**Предусловие:** Существование двух таблиц
**Основной сценарий:**
1. Преподаватель запускает скрипт для связи таблиц
2. Работа скрипта
3. ПРиложение выдает подтверждение и информацию. Запись в лог
**Результат:** Данные из одной таблицы автоматически скопированы в другую

### Use Case 3: Связь таблиц и формы
**Действующее лицо:** Преподаватель
**Предусловие:** Существование формы и таблицы для результатов
**Основной сценарий:**
1. Преподаватель запускает скрипт привязки формы
2. Приложение настраивает связь между формой и таблицей
3. При заполнении формы пользователем, скрипт автоматически добавляет информацию в таблицу

**Результат:** Ответы студентов автоматически появляются в таблице

### Use Case 4: Управление правами доступа (уточнить)
**Действующее лицо:** Преподаватель
**Предусловие:** Существование таблицы. Целевой пользователь зарегестрирован в системе
**Основной сценарий:**
1. Преподаватель запускает скрипт управления доступом
2. Преподаватель вводит необходимые данные
3. Приложение обновляет данные для указанного пользователя
4. Приложение уведомляет целевого пользователя о том, что ему предоставили права на таблицу.

**Результат:** Доступ к таблице предоставлен целевому пользователю

### Use Case 5: Commitment 
**Действующее лицо:** Преподаватель
**Основной сценарий:**
1. Преподаватель запускает скрипт
2. Скрипт берет ссылки на репозитории из таблицы, считает коммиты студентов и записывает результат обратно в таблицу
3. Приложение рассчитывает итоговый показатель участия на основе заданных алгоритмов
4. Приложение автоматически обновляет данные в исходной таблице

**Результат:** Получены оценки об активности студентов без необходимости ручного анализа каждого репозитория

## 3. Студент 

### Use Case 1: Просмотр таблицы
**Действующее лицо:** Студент
**Предусловие:** Существование таблицы. Условие того, что она открыта для просмотра 
**Основной сценарий:**
1. Студент открывает веб-ссылку на таблицу, предоставленную преподавателем
2. Студент просматривает необходимую информацию
