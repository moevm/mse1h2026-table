# Сценарии использования
*Сценарии использования описывают взаимодействие пользователей с системой на уровне действий и результатов, без привязки к реализации интерфейса или внутренним скриптам.*  

**Роли в проекте:**
1. **Администратор** - отвечает за развертывание, техническое состояние и сохранность данных системы.  
2. **Преподаватель** - создает формы и таблицы, управляет доступами, организует сбор данных.  
3. **Студент** - заполняет формы, просматривает результаты.  

*Примечание: Категоризация пользователей является условной и не отражает логическое разделение пользователей.*

___

## 1. Пользовательские сценарии
*Эти сценарии описывают жизненный цикл учебного процесса. Преподаватели и студенты взаимодействуют с интерфейсом таблиц как конечные пользователи.*  
### Use Case 1: Организация сбора данных через формы
**Действующее лицо:** Преподаватель.    
**Предусловие:** Преподаватель авторизован в системе.  
**Основной сценарий:**  
1. Преподаватель создает новую таблицу через интерфейс системы.
2. Преподаватель настраивает структуру таблицы: добавляет необходимые столбцы и задает формулы для автоматической обработки результатов.
3. Преподаватель создает форму сбора данных и определяет типы полей ввода.
4. В настройках формы преподаватель указывает целевую таблицу для автоматического сохранения ответов.
5. Система автоматически создает связь между формой и таблицей.
6. Преподаватель предоставляет студентам доступ к форме (на заполнение).
7. При заполнении формы студентами данные отображаются в таблице в режиме реального времени.

**Результат:** Настроена автоматическая цепочка сбора данных через форму и таблицу.  

### Use Case 2: Управление доступом к таблицам и формам
**Действующее лицо:** Преподаватель.  
**Основной сценарий:**  
1. Преподаватель открывает настройки доступа через интерфейс системы.
2. Преподаватель добавляет конкретных пользователей или включает доступ по ссылке.
3. Преподаватель назначает соответствующие права.
4. Пользователи получают доступ согласно назначенным правам.

**Результат:** Права доступа к данным настроены и применяются согласно назначенным разрешениям пользователей.

### Use Case 3: Синхронизация данных между таблицами (Import Range)
**Действующее лицо:** Преподаватель.  
**Предусловие:** В системе созданы две таблицы.  
**Основной сценарий:**  
1. Преподаватель в Таблице А использует формулу (аналог Import Range), указывая ссылку на диапазон данных из Таблицы Б.
2. Система устанавливает динамическую связь между таблицами.
3. При изменении данных в Таблице Б изменения автоматически отображаются в Таблице А без ручного копирования.

**Результат:** Реализована автоматическая синхронизация данных без копирования.

### Use Case 4: Экспорт данных в систему таблиц через адаптер
**Действующее лицо:** Преподаватель.  
**Предусловие:** Развернута система таблиц. Настроен модуль импорта (адаптер). Данные доступны в виде экспортного файла (например, CSV), сформированного внешним инструментом.
**Основной сценарий:**  
1. Преподаватель запускает внешний экспортёр данных (например, GitLogger / LMS exporter) и получает CSV-файл.
2. Преподаватель запускает модуль импорта (адаптер) и передает ему CSV-файл и целевую таблицу
3. Модуль импорта загружает данные в выбранную систему таблиц.
4. Модуль импорта сопоставляет загруженные данные с существующими строками таблицы по согласованным правилам и обновляет записи.

**Результат:** Данные из внешнего источника загружены и обновлены в системе таблиц через модуль импорта (адаптер), без привязки к конкретному источнику данных и формату внутренней таблицы.

### Use Case 5: Студент заполняет форму и просматривает таблицу
**Действующее лицо:** Студент.  
**Основной сценарий:**  
1. Студент переходит по ссылке на форму, предоставленную преподавателем.
2. Студент заполняет необходимые поля и отправляет ответ.
3. Таблица обновляется в режиме реального времени без перезагрузки страницы. Данные из формы попадают в таблицу в режиме реального времени.
4. Студент переходит по ссылке на таблицу для просмотра результатов и видит свои данные без задержек.

**Альтернативный сценарий (Нет доступа):**
1. Студент пытается открыть таблицу по ссылке, на которую у него нет прав.
2. Система определяет отсутствие прав и выводит сообщение об отказе в доступе.

**Результат:** Данные студента сохраняются и отображаются в таблице без перезагрузки страницы, обеспечивая согласованное состояние формы и таблицы в режиме реального времени.

## 2. Эксплуатационные сценарии
*Эти сценарии описывают работу администратора и скриптов, которые обеспечивают жизнедеятельность системы.*  

### Use Case 1: Автоматизированный деплой системы
**Действующее лицо:** Администратор.  
**Предусловие:** На сервере установлены все зависимости, подготовлены файлы конфигурации.  
**Основной сценарий:**  
1. Администратор запускает скрипт деплоя.
2. Скрипт проверяет настройки Docker, а также наличие свободных портов.
3. Приложение разворачивает контейнеры (БД, сервис таблиц, сервис форм) и выполняет автоматическую настройку интеграции между сервисами.
4. Система выводит сообщение об успешном запуске и URL-адреса развернутых сервисов.

**Альтернативный сценарий:**
1. Скрипт обнаруживает конфликт портов или нехватку прав.
2. Процесс прерывается, приложение выводит сообщение с указанием ошибки.

**Результат:** Система развернута и готова к работе.

### Use Case 2: Проверка статуса системы (Health-check)
**Действующее лицо:** Администратор.  
**Предусловие:** Система была предварительно развернута.  
**Основной сценарий:**  
1. Администратор запускает скрипт проверки статуса.
2. Приложение опрашивает каждый контейнер на предмет активности (статус Running).
3. Приложение проверяет наличие соединения с базой данных и отклик API (код 200).
4. Приложение выводит краткий отчет о доступности всех компонентов.

**Результат:** Получена актуальная информация о состоянии всех элементов системы.

### Use Case 3: Мониторинг ресурсов и аналитика нагрузки
**Действующее лицо:** Администратор.  
**Основной сценарий:**  
1. Администратор запускает скрипт сбора метрик.
2. Приложение собирает данные: CPU, RAM, количество активных сессий, среднее время отклика API.
3. Приложение формирует отчет (в формате JSON или HTML) с данными по нагрузке.

**Результат:** Получена актуальная информация о нагрузке системы.

### Use Case 4: Нагрузочное тестирование
**Действующее лицо:** Администратор.  
**Основной сценарий:**  
1. Администратор запускает сценарий нагрузочного тестирования.
2. Система эмулирует работу типовых пользовательских сценариев до заданного числа пользователей.
3. Система фиксирует данные: время отклика, ошибки запросов, потребление ресурсов.
4. Приложение формирует отчет (в формате JSON или HTML) с данными по нагрузке.

**Результат:** Получены показатели устойчивости системы при высокой нагрузке.

### Use Case 5: Резервное копирование и восстановление
**Действующее лицо:** Администратор.  
**Предусловие:** Система запущена, содержит пользовательские данные.  
**Основной сценарий (Создание бэкапа):**
1. Администратор запускает скрипт создания бэкапа.
2. Приложение создает дамп базы данных и архивирует файлы конфигурации.
3. Архив (артефакт .tar.gz / .zip) сохраняется в файловой системе сервера.

**Альтернативный сценарий (Ошибка создания бэкапа):**
1. На диске недостаточно места для создания архива, или возникла другая техническая причина, по которой бэкап не может быть создан.
2. Скрипт прерывает работу и возвращает сообщение о соответствующей ошибке.

**Результат:** Успешно создана резервная копия данных.  

**Сценарий восстановления:**
1. Администратор запускает скрипт восстановления, указывая бэкап.
2. Система восстанавливает структуру БД и данные, после чего перезапускает сервисы.

**Результат:** Данные успешно восстановлены из копии.
